## 核心心智模型

### 模型 1：双重塔尖战略（Oracle RAC 兼容 + 100% 自研内核）

**一句话**：在国产数据库领域，崖山是唯一同时追求「Oracle RAC 等价替代」和「100% 自研内核」的厂商，这是最艰难的「双重塔尖」定位。

**证据**：
- 金仓、达梦走「主路 PG/MySQL 兼容 + 集中式」；OceanBase 走「分布式原生 + 蚂蚁生态」；只有 YashanDB 走「Oracle RAC 兼容 + 100% 自研内核」（Agent 4/5 反复出现）
- 陈志标 2024-05 湾区科技评论访谈：「如果要和 Oracle 竞争，走开源的道路是不行的」
- 「3 不变 2 对等 1 更优」口号自 2024-11 创新生态大会起高频出现，强调 Oracle PL/SQL、SQL 语法、存储过程不变

**应用**：
- 评估「崖山 vs OceanBase vs PolarDB vs 金仓」时，先问业务核心场景是 Oracle RAC 兼容还是分布式扩展
- 评估「100% 自研」时，区分「方法学未公开的官方主张」与「同行 90% 自主的对照措辞」
- 判断是否值得为「双重塔尖」承担更高 License 成本和服务投入

**局限**：
- 同时做三种部署形态（单机/分布式/共享集群）让研发资源分散，单一形态成熟度可能不如专注厂商
- 100% 自研的方法学未公开，与同行"90% 自主"形成显著差异，对比时需谨慎
- 双塔尖导致某些场景并非最优：超大规模分析不如专用 MPP OLAP（如 Doris/ClickHouse），互联网高并发不如 TiDB

**一句话**：从樊文飞院士的顶会论文到 V23.5 的 618 万 tpmC，崖山坚持「学术资产 → 内核实现 → 客户落地」的闭环链路，「院士+顶会+全栈」组合在国产数据库中独一无二。

**证据**：

### 模型 3：窄而深客户策略（100+ 客户但质量极高）

**一句话**：客户基数绝对数量小（100+ vs OB 4000+/达梦数千/金仓数千），但客户质量极高（央行数研所、华润银行、国信证券、Kaspi 银行等），形成「窄而深」格局。

**证据**：
- 央行数研所「数字人民币联防联控系统」是少数明确公开案例（30 分钟切换）
- 已获 44 家金融机构认证，覆盖 80+ 金融系统
- 第一新声智库 2025 金融报告将 YashanDB 列为「可用/可靠性、单节点性能、TCO 三项第一」
- 客户原始问题中"博时基金/华润银行/国信证券"多为"集中签约"或"兼容互认证"阶段，真实生产规模、稳定性记录、性能数据公开披露深度不足

**应用**：
- 评估崖山时区分「官方案客户数」与「真实生产核心案例数」
- 客户质量背书（央行数研所）是金融核心选型的重要参考
- 在 POC 评估中，优先参考央行数研所、深圳燃气、王若楠 YAC 实测等可验证案例

**局限**：
- 100+ 客户基数小，意味着社区生态、二次开发商、问题案例库都不如成熟厂商
- 客户质量高不代表迁移/运维成本低，可能存在"重投入大客户、轻投入中小客户"的不对称服务
- 海外仅 1 例（Kaspi 银行），与官方"出海"宣传存在落差

### 模型 4：全栈自研 + 全形态部署

**一句话**：崖山不基于任何开源内核，同时做单机主备、分布式（MN+CN+DN）、共享集群 YAC 三种部署形态，覆盖 OLTP/HTAP/OLAP 全场景。

**证据**：
- 100% 内核代码自主率（官方主张，方法学未公开）
- 三种部署形态并列，非选择题：
  - 单机主备：1主多备，同步/异步复制，故障自动切换
  - 分布式：Shared-Nothing 架构，MN（管理）+ CN（协调）+ DN（数据）三类节点
  - 共享集群 YAC：共享存储 + Cohesive Memory 全局缓存，多实例多写多活
- 四种存储结构：HEAP（行存 OLTP）/ BTREE（索引）/ MCOL（可变列存 HTAP）/ SCOL（稳态列存 OLAP）
- V23.x 升级为 TAC（事务列存表）/ LSC（大规模列存表）

**应用**：
- 架构选型时，根据业务场景匹配形态：OLTP → 单机主备/分布式；HTAP → 单机 MCOL/分布式；金融核心 → 共享集群 YAC
- 不要假设"自研 = 比开源好"或"自研 = 比开源差"，需结合客户场景独立评估
- 三种形态都有，要识别每种形态的最佳实践和已知局限

**局限**：
- 同时做三种形态，研发资源分散，单一形态成熟度可能不如专注厂商
- 共享集群 YAC 是国产数据库中除达梦 DMDSC 外唯一坚持 Shared-Disk 路线的厂商——技术独特但生态相对封闭
- 「全栈自研 + 全形态」成本高，License 与服务价格可能高于专注厂商

### 模型 5：国测过测 = 入场券

**一句话**：中国信息安全测评中心「安全可靠测评」是政府采购、金融核心、政务央国企选型的入场券，崖山是公开可查中唯一「全栈自研+双形态」II 级过测厂商。

**证据**：
- 2025-08-22 通过国测 I 级（集中式）
- 2025-08 至 2026-05 一年内连续通过国测 II 级（分布式）
- 截至 2026-05，崖山是国测双形态过测等级最高的厂商（I+II 双形态）
- 信通院"可信数据库"关系型安全测试过测
- 2026 起金融核心系统国产化进入交付投产期，200-300 家中小银行 70-80% 在 2025-2026 完成选型

**应用**：
- 政府/金融/政务/央国企客户选型时，优先确认候选厂商是否过测及过测等级
- 国测过测是必要条件，不是充分条件——需结合客户案例、POC 结果综合评估
- 「国测 I+II 双料」是崖山最强的入场券标签，竞品对比中要突出

**局限**：
- 过测不等于最优，过测是基础门槛
- 双料过测不能替代客户场景的深度 POC
- 过测标准在持续演进，需关注最新版本过测情况

### 模型 6：从塔尖到塔基扩展策略

**一句话**：从「Oracle 高端核心 1:1 平替」起步，2024-11（V23.3）后加入 MySQL 兼容，开始向中小型客户、SaaS、互联网场景延伸，是从「塔尖」向「塔基」扩展的策略信号。

**证据**：
- V22.2（2023）到 V23.2（2024-04）都是 Oracle 兼容为主
- V23.3 / V23.4 LTS（2024-11）加入 MySQL 5.7/8.0 兼容，通过 `SQL_PLUGIN='MYSQL'` 参数切换
- V23.4 LTS 全协议兼容 180+ MySQL 同名函数
- V23.5（2025-12）进一步强化多模态
- 这与陈志标"不做开源组装厂"的立场形成有趣并列——崖山不基于 MySQL 内核，但要做 MySQL 协议的兼容层

**应用**：
- 评估 MySQL 业务迁移到崖山的可行性时，确认版本 ≥ V23.3
- V23.3 之前的版本不能用于 MySQL 业务
- Oracle 业务迁移优先 V23.2 LTS 或 V23.4 LTS（推荐 LTS 版本）

**局限**：
- MySQL 兼容是 2024-11 后才补齐，V23.3 之前的所有"兼容性叙事"只围绕 Oracle
- MySQL 兼容层的稳定性、性能、生态成熟度需要更多第三方实测
- 同时维护 Oracle + MySQL 两套兼容层，研发资源分散风险

## 决策启发式

### 1. POC 优先于承诺

**规则**：所有兼容性宣称必须 POC 验证，「1:1 平替 Oracle」实测有 387 项差异，DBA 需付出调试成本。

**应用场景**：
- 任何 Oracle/MySQL/PG → 崖山迁移项目
- 涉及 LAST_DAY()、隐式类型转换、LISTAGG()、字符串内分号等已知差异点
- MyBatis-Plus 默认不识别 YashanDB 方言，需要伪装成 Oracle/MySQL 方言

**案例**：王若楠（前泽塔数科研发总监）公开质疑后实测承认 YAC「稳定性、成熟度、独特性超出预期」，但实测中仍有多个差异点需调整。

### 2. 测试用例驱动质量

**规则**：百万级测试用例 + 300+ 物理服务器 7×24 + 每年近 2 亿研发投入，是崖山的质量承诺。

**应用场景**：
- 评估崖山与同类产品的质量基准
- 谈判 SLA 时参考崖山的测试基础设施
- 关注官方公布的百万级测试用例覆盖范围（功能/性能/兼容性）

**案例**：陈志标在多场演讲中反复引用这些数据，但未见第三方独立审计。

### 3. 国测过测是核心门槛

**规则**：信创/金融/政务选型，国测过测是入场券。崖山是公开可查中唯一「全栈自研+双形态」II 级过测厂商。

**应用场景**：
- 政府/金融/政务/央国企客户选型
- 信创目录查询
- 投标资质审核

**案例**：2025-08-22 通过国测 I+II 双料过测后，业务明显加速；2025-12 V23.5 共享集群规模化商用；2026-03 Kaspi 银行出海。

### 4. 共享集群 + Cohesive Memory 是 YAC 的核心差异化

**规则**：在国产数据库主流走分布式路线绕开 Oracle RAC 的当下，YAC + Cohesive Memory 是崖山"1:1 平替 Oracle"定位的技术基础。

**应用场景**：
- 金融核心系统、运营商计费、政务关键业务
- 需要 RPO=0、RTO<15s 的强一致场景
- 多实例多写多活的高端 OLTP

**案例**：王若楠独立验证 YAC 4 节点 520 万 tpmC，RPO=0、RTO<15s。V23.5 国内首个类 Oracle SCAN/VIP/TAF。

### 5. 多形态部署覆盖全场景

**规则**：单机主备 / 分布式（MN+CN+DN）/ 共享集群 YAC 各有边界场景，不可混淆。

**应用场景**：
| 业务场景 | 推荐形态 | 理由 |
|---------|---------|------|
| 中小型 OLTP、单机房 | 单机主备 | 简单、够用、成本低 |
| 海量数据分析、HTAP、线性扩展 | 分布式（MN+CN+DN） | Shared-Nothing 横向扩展 |
| 金融核心、强一致、多写多活 | 共享集群 YAC | 共享存储 + Cohesive Memory |
| 政务关键业务 | 共享集群 YAC 或单机主备 | 看业务连续性要求 |

**案例**：央行数研所「数字人民币联防联控系统」使用 YAC 共享集群，30 分钟切换。

### 6. 性能数据必须标注测试背景

**规则**：TPC-C 数字必须区分「厂商自测 vs TPC 官方审计」「BenchmarkSQL vs TPC-C 基准」。

**应用场景**：
- 引用任何性能数字（210 万 / 312 万 / 520 万 / 618 万 tpmC）
- 与同类产品对比
- 客户沟通中的性能承诺

**案例**：TPC 官网无 YashanDB 审计记录，所有数字均为厂商基于 BenchmarkSQL 的自测，硬件配置/扩展比未完整披露。第一新声智库引用的"超 Oracle RAC 30%"也需注明出处。

### 7. 金融优先 + 地理红利

**规则**：金融是行业优先（议价能力高），但实际最早落地是深圳本地政务（龙华区、深圳市级）和深圳本地国央企。院士+研究院+龙华区共建三位一体的地方关系是早期客户突破口。

**应用场景**：
- 客户行业选择：金融 > 政务 > 能源 > 运营商
- 地理优先级：深圳本地 > 北京/上海 > 其他省会
- 集成商选择：深智城、海光-中科曙光等深圳生态

**案例**：2023-11-17 集中签约 7 家深圳本地企业近亿元（深圳燃气、环水、地铁等）；2024-12 央行数研所案例；2025-08 东方证券；2026-03 Kaspi 银行。

### 8. MySQL 兼容是塔基扩展策略

**规则**：V23.3（2024-11）后加入 MySQL 5.7/8.0 兼容，是从「塔尖」向「塔基」扩展的策略信号。

**应用场景**：
- 评估 MySQL 业务迁移时确认版本 ≥ V23.3
- 互联网、SaaS、中小型客户场景
- 与 MySQL 生态工具链对接（MyBatis-Plus 需要伪装方言）

**案例**：V23.4 LTS 全协议兼容 180+ MySQL 同名函数，通过 `SQL_PLUGIN='MYSQL'` 参数切换。

### 9. 不开源是商业立场

**规则**：崖山不基于任何开源内核，坚持 100% 自研。陈志标明确表态「走开源的道路是不行的」。

**应用场景**：
- 评估是否需要开源生态对接（答案：需通过兼容层）
- 评估 License 与服务模式
- 评估产品演进可控性（vs 基于开源的厂商）

**案例**：陈志标 2024-05 湾区科技评论访谈：「如果要和 Oracle 竞争，走开源的道路是不行的」；自述「国内最早一批对 PostgreSQL 内核做修改」。

### 10. 理论-产品-客户闭环

**规则**：原创理论必须能工程化落地到客户场景。深算院 121 篇论文 → YashanDB 内核 → 44 家金融机构认证。

**应用场景**：
- 评估「院士领衔」的实质价值：学术严谨度（顶会论文可验证）vs 工程转化率（生产稳定性需客户验证）
- 在 POC 中识别理论叙事与实际表现的差距
- 关注学术奖项对产品的实际推动（ICDE 2024 最佳论文 → V23.x 哪些特性？）

**案例**：樊文飞 ICDE 2024 最佳论文《Reverse Regret Query》、VLDB 2024 最佳系统演示奖（"去病"系统）。中国电子学会鉴定「资源受限计算 + 跨模融合查询」达到国际领先。

## 诚实边界
